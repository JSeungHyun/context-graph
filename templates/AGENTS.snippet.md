## ⭐ 요구가 들어오면 이 순서로 탐색한다

```
1. node tools/graph-find.mjs <용어…>      ← 과거 유사 요구 + 그때 만진 파일. 있으면 시작점이 공짜다
   node tools/graph-find.mjs --with <파일>  ← 그 파일을 고칠 때 같이 움직이는 파일 (2홉)
2. <어휘 정본 문서 — 있으면. 현업 용어 → 코드 식별자>
3. ⭐ DB 코멘트                            ← 컬럼·코드값의 의미를 묻는 것이면 여기가 가장 싸다 (아래)
4. <관통 조회 도구 — 있으면>
5. <규격 문서 해당 절만>
6. <정밀 탐색 — LSP MCP 가 있으면 그것, 없으면 Grep / Glob>
```

⛔ **1번을 건너뛰지 않는다.** 같은 주제를 두 번째 풀 때 처음부터 다시 탐색하는 것이 가장 큰 낭비다.
⚠️ 1번이 빈손이면 **새 영역이다.** 그때는 2번부터 정상 탐색한다.
⭐ **어근을 짧게, 여러 개 준다.** 부분일치라 조사·접미사가 붙으면 놓친다 — 「문의하기」 0건, 「문의」 3건.

### ⭐⭐ 3번 — 컬럼·코드값의 의미는 DB 코멘트에 있다

⛔ **DB 를 쓰는 프로젝트면 이 원천을 먼저 확인한다.** 실측(APMS): 한 스키마에 컬럼 코멘트가 **1,437개**
있었는데 몇 달간 한 번도 쓰지 않았고, 코드로 힘들게 알아낸 것들이 코멘트에 이미 있었다.

```bash
# PostgreSQL — 특정 테이블의 전 컬럼 코멘트
psql … -tAc "select a.attname, d.description from pg_description d
 join pg_class c on c.oid=d.objoid join pg_namespace n on n.oid=c.relnamespace
 join pg_attribute a on a.attrelid=c.oid and a.attnum=d.objsubid
 where n.nspname='<스키마>' and c.relname='<테이블>' order by a.attnum;"

# 낱말로 역방향 — 「이 현업 용어가 어느 컬럼인가」
… and d.description like '%<낱말>%';
```

⭐ **코멘트에 값 의미의 변경 이력이 `->` 로 남아 있는 경우가 있다.** 앞이 과거, **뒤가 현재**다.

#### ⛔⛔ 코멘트도 잔존한다 — 「의미」는 주지만 「쓰이는지」는 안 준다

⚠️ 실측 사례: 코멘트에 값 4종이 적혀 있었는데 **실제 데이터는 2종뿐**이었고, 나머지 하나는
다른 컬럼이 그 역할을 하고 있었다. 코멘트만 보고 살아 있는 값으로 기록했다가 지적받아 정정했다.

```bash
… -tAc "select <컬럼>, count(*) from <테이블> group by 1 order by 2 desc;"   # 값이 실제로 있나
grep -c "<컬럼>" <매퍼·쿼리 디렉터리>/* | grep -v ':0'                        # 코드가 쓰나
```

⇒ **「단일 증거로 단정하지 않는다」가 코멘트에도 적용된다.** 코멘트는 어휘 다리로 쓰고,
살아 있는지는 **값 분포 + 코드 참조**로 판정한다.
⛔ 새 원천을 찾으면 그 원천을 과신하게 된다 — **원천이 늘어날 때마다 이 규칙을 다시 적용한다.**

### ⛔⛔ 코드 탐색은 세 경우에만 한다

그래프·참조 파일에 답이 있으면 **그것을 그대로 옮겨 답한다.** 코드·DB 를 다시 파는 것은 아래 셋뿐이다.

| 경우 | 범위 |
|---|---|
| ① 컨텍스트에 정답이 없다 | 훅·`graph-find` 가 못 찾았거나, 찾은 기록에 그 물음의 답이 없다 |
| ② 컨텍스트로 답한 것이 부족하다고 사용자가 말했다 | 그 부족한 대목만 |
| ③ 사용자가 더 보라고 지시했다 | 지시한 범위만 |

⛔ 기록에 `⚠️ 미확정` 이 붙지 않은 항목을 「확인차」 코드로 다시 보지 않는다 — 기록을 안 믿으면 기록 비용만 남는다.
⚠️ 실측 사례: 운영 절차 하나가 그래프에 있었는데 스키마 덤프·서비스 재확인으로 도구 호출 7회를 썼고,
사용자가 「매번 이 비용이면 이 구조를 채택할 이유가 없다」고 했다. 답하면서 새로 알게 된 것은 **그 자리에서 정본 기록에 넣는다**.

⭐ 절차형 질문(「…요건이 오면 뭘 확인하고 어디에 넣나」)은 **`정본: ` 으로 시작하는 기록**이 답이다. 절차와 참조 SQL 템플릿을 채워 붙이고,
템플릿이 낡았는지는 `node tools/sql-template-check.mjs <템플릿.sql>` 한 줄로 본다(스키마는 `PGSCHEMA` 환경변수, 기본 apms).
⭐ 사용자의 표현이 기록 키에 없으면 **답을 찾은 그 턴에** `graph-alias` 로 등록한다 — 표현 하나가 빠져 훅·CLI 모두 정본을 못 찾은 실측이 있다.

### ⛔ 「버그다」라고 말하기 전에 호출 사슬을 끝까지 읽는다

한 층만 보고 단정하지 않는다. **진입점 → 중간 계층 → 최종 실행부**를 다 열고 판정한다 —
값이 「그대로 전달되는 것처럼」 보여도 중간 계층에서 가공했을 수 있다.

```bash
<중간 계층 호출부를 찾는 명령 — 예: grep -rn "<메서드명>" <서비스 계층 경로>>
```

⛔ 사슬을 다 못 읽었으면 「버그다」가 아니라 **「<본 층>만 보면 …인데 <안 본 층>은 확인 못 했다」** 로 말한다.
확신이 낮은 주장을 `⚠️ 미확정` 없이 그래프에 넣지 않는다 — 다음 세션의 내가 그것을 사실로 믿는다.
⚠️ 실제 사고(APMS, 2026-09-08): 매퍼 XML 한 줄과 JSP 만 보고 「이 화면에서 저장하면 데이터가 사라진다」고
단정해 사용자에게 설명하고 그래프에까지 남겼다. 서비스 구현체에 값 변환 루프가 있어 실제로는 안전했다.

### ⭐⛔ 사용자가 쓴 말이 그래프에 없으면 그 자리에서 배운다

사용자의 표현으로 조회해 **0건이면 어휘 다리가 빠진 것**이다. 코드를 파서 실체를 알아낸 뒤,
**사용자가 실제로 쓴 그 말을 키로** 기록한다. 작업이 끝나기를 기다리지 않는다 — 용어는 대화 중에 드러나고 그때 안 적으면 사라진다.

```bash
node tools/graph-alias.mjs <사용자가 쓴 말> "<시스템에서 무엇인가>" [--file 경로]… [--note 함정]
```

⛔ **키는 사용자의 말, 값은 시스템의 실체다.** 공식 용어를 키로 적으면 다음에도 똑같이 못 찾는다.
⛔ **알아내기 전에 적지 않는다.** 추측을 적으면 다음 세션이 그것을 사실로 믿는다.
⭐ 같은 것을 다르게 부르면 그때마다 한 줄씩 더 적는다. 별칭이 쌓일수록 걸리는 폭이 넓어진다.
⛔ **용어 키는 그 용어의 정본 기록에만 둔다.** 도구·설정 작업 기록에 도메인 용어를 *예시로* 넣으면
그 용어의 정본 기록을 순위에서 밀어낸다 (2026-09-04 실측 — 상위 2건 중 정본이 2위로 밀렸다).
⛔⛔ **예시 낱말을 어느 필드에도 넣지 않는다 — 전 필드가 색인된다**(`req`·용어 키·용어 값·`tables`·`files`·`note`).
이 줄은 원래 「예시는 `note` 나 `req` 본문에 쓴다 — 가중치가 낮아 정본을 밀지 않는다」였다. **틀렸다** — 그 조언대로 적어 세 번 오염시켰다.
예시가 필요하면 낱말이 아니라 성격을 쓴다.

⚠️ **조사·띄어쓰기는 저장하지 않는다.** 「재무지표가」·「재무 지표」는 질의 쪽에서 규칙으로 만든다
(`graph-find.mjs` 의 `tokenizeKo` — 훅과 CLI 가 같은 토크나이저를 쓴다). 저장 쪽에 넣으면 색인이 2.7배가 되는데 새 지식은 0이다.
⇒ **규칙으로 만들 수 있으면 질의 때 만들고, 못 만들면(동의어·약어) 저장한다.**

### ⛔ 작업이 끝나면 요구 → 파일 간선을 기록한다

작업 파일 목록을 사용자에게 보고할 때 **같은 내용을 그래프에도 append 한다.**

```bash
node tools/graph-append.mjs <<'EOF'
{"req":"<사용자 요구 한 줄>",
 "terms":{"현업 용어":"시스템에서 무엇인가 (테이블·URL·컬럼·서비스)"},
 "tables":["<스키마>.<테이블>", "…"],
 "files":["실제로 만진 파일 경로…"],
 "note":"다음 사람이 알아야 할 함정 한 줄"}
EOF
```

⭐ **`terms` 는 객체로 쓴다** — 「경영주기 → `base_year`」처럼 **무엇을 의미하는지**까지 담는다.
배열(`["용어","용어"]`)로 쓰면 용어만 남고 해석이 사라진다.
⭐ **DB 를 만졌으면 `tables` 에 스키마 접두어까지** 적는다 — 「이 용어가 어느 테이블인가」가 가장 자주 필요한 질문이고,
접두어가 없으면 이름이 겹치는 다른 스키마의 표와 구분되지 않는다.
⭐ **`note` 가 이 기록의 값이다.** 파일 목록은 git 으로도 알 수 있지만 「왜 그 파일이었나」는 여기에만 남는다.
⭐ **미구현·중단된 것도 기록한다.** 「거기까지 알아냈고 왜 멈췼나」가 다음 시도의 출발점이다.
⛔⛔ **다만 하다 만 것은 `note` 를 `⏸` 로 시작해야 한다 — 그게 유일한 노출 경로다.** 아래 절 참조.
⭐ **반복 운영 절차는 사실 조각이 아니라 `정본: ` 기록 1건 + `tools/graph/sql/` 템플릿으로** 남긴다(스킬 §2 「절차는 정본 1건 + 템플릿 파일」).
템플릿 낡음은 `node tools/sql-template-check.mjs <파일>` 한 줄로 잰다. 절차 질문에는 정본을 **그대로 옮겨** 답하고 코드를 다시 파지 않는다.
⛔ **기록 저장소는 자동 로드되지 않는다** — `requests.jsonl` 은 조회로만 읽으므로 무한히 커져도 세션 비용이 0이다.
(훅을 붙였다면 자동으로 들어오는 것은 **저장소가 아니라 상한이 걸린 조회 결과 2건**이다. 원칙은 유지된다.)

### ⛔⛔ 하다 만 것은 `note` 를 `⏸` 로 시작한다 — 그게 유일한 노출 경로다

적어 두는 것만으로는 다음 세션이 못 찾는다. 랭킹이 평평한 키워드 합산이라 **항목이 많은 광역 기록이 도메인 낱말을 독점한다.**

⚠️ 실측 사례: 설계까지 해두고 멈춘 보류 기록이 **그 작업을 재개하는 요청**에서 10위였다.
훅은 1~2건, CLI 는 5건만 보여주므로 닿을 방법이 없었고, 기록이 있는데 못 꺼내 세션 로그를 3분 36초 뒤졌다.

```json
{"req":"…", "note":"⏸ 어디까지 했고 왜 멈췄나 · 재개하려면 무엇만 받으면 되나"}
```

⭐ `⏸` 가 붙으면 훅이 **순위 밖이어도** 「⏸ 열린 작업」 줄로 붙여 준다(그 주제 점수가 5 이상일 때만).
⭐ 「뭐 하다 말았나」는 `node tools/graph-find.mjs --open` 으로 전부 본다.
⛔ **낱말(「미구현」·「보류」)로는 판정하지 않는다** — 그렇게 넓혀 재 봤더니 3건 중 2건이 오탐이었다.
절차는 끝났는데 곁가지 권고만 안 된 정본 같은 것이 딸려 온다. **표식은 사람이 붙이고 기계는 후보만 올린다.**
⛔ 표식은 `note` **맨 앞**에서만 인정한다 — 본문 어디서나 찾으면 이 규약을 설명하는 기록이 스스로 걸린다.
⛔ **재개해서 끝냈으면 그 기록을 `supersedes` 로 무효화한다.** `⏸` 를 지우는 것으로 갈음하지 않는다.

⭐ 이것은 랭킹을 고친 것이 아니라 **축을 하나 늘린 것**이다. 「하다 만 것」은 점수로 이길 수 없는 종류의 기록이라
상태로 빼냈다. 랭킹은 건드리지 않았고 회귀 지표(req 자기검색)는 불변이었다.

### ⛔ 기능을 바꿔 기존 기록이 낡으면 그 자리에서 무효화한다

⭐⭐ **같은 주제의 살아있는 기록이 2건 이상이면 다음에 손댈 때 정본 1건으로 통합한다** — 사실을 더 쌓지 않는다.
`"supersedes":["<req1>","<req2>",…]` 배열로 전부 무효화하고, 정본의 `req` 는 `정본: ` 으로 시작한다.
⚠️ 조각이 흩어져 있으면 찾은 뒤에도 조립이 답변 비용이 된다 — 절차 하나가 5건에 흩어져 있던 실측이 있다.

새 기록을 추가하는 것으로 갈음하지 않는다. **판단 기준은 「이 기록을 그대로 믿고 작업하면 틀리나」** — 틀리면 낡은 것이다.

| 낡은 것 | 할 일 |
|---|---|
| `requests.jsonl` 의 이전 기록 | 새 기록에 `"supersedes":"<이전 기록의 req>"` (여러 건을 정본 하나로 모으면 배열) |
| <어휘 정본 문서> | 어긋난 줄을 고친다 |
| <규격 문서> | 근거(`파일:라인`)와 함께 반영 |

⛔ **별개 작업이면 비운다.** 같은 화면을 만졌다고 다 대체가 아니다.
⚠️ `supersedes` 는 **`req` 문자열로 잇는다** — 한 글자만 달라도 사슬이 끊긴다. `--check` 로 확인한다.
⭐ `date` 는 **세상 시간**(작업이 일어난 때), `recorded` 는 **기록 시간**(줄을 쓴 때). 과거를 소급 기록할 때만 `date` 를 직접 준다.

### 주기적으로 — 검증과 승격

```bash
node tools/graph-find.mjs --check                    # 무결성 5절 — 사슬·경로·용어 선점·열린 작업 표식·시간 (이상 있으면 exit 1)
node tools/graph-find.mjs --open                     # 하다 만 것(⏸) 전부
node tools/graph-find.mjs --promote <어휘 정본 문서>   # 3회 이상 등장 + 정본에 없는 용어
node tools/graph-view.mjs                            # 전체를 브라우저 한 장으로
```

⛔ **`--check` 가 낡음을 세 방향으로 잡는다.** 「경로 무결성」은 참조 경로가 사라진 기록을,
「용어 선점」은 같은 용어에서 과거 기록이 조회 1위인 것을 잡는다 — 그대로 두면 새 세션이 낡은 값을 답한다.
「열린 작업 표식」은 하다 만 것처럼 쓰였는데 `⏸` 가 없는 기록을 후보로 올린다(경고, exit 0) — 표식이 없으면 훅이 못 붙인다.

## ⛔ 작업 흐름 — `writing-plans` 를 쓰지 않는다

<!-- ⚠️ 이 절은 superpowers + ponytail 조합을 쓸 때만 넣는다. 안 쓰면 삭제한다. -->

```
brainstorming (superpowers)   요건·설계를 대화로 확정
      ↓  ⛔ writing-plans 생략 — 계획 문서를 만들지 않는다
구현                          ponytail 결정 사다리를 매 판단마다 적용
      ↓
검증                          <테스트 명령>  →  /ponytail-review (과설계)  →  /code-review (정확성)
```

⛔ **brainstorming 스킬은 종료 조건이 「writing-plans 호출」로 박혀 있다. 이 지침이 그것을 무효화한다.**
사용자 지침이 스킬보다 우선한다.

⚠️ **파일 5개 이상이거나 의존 순서가 있으면** `TodoWrite` 로 단계만 나열한다 — 문서는 만들지 않는다.
⭐ 계획을 없앤 대신 **판단 시점이 구현 순간으로 옮겨진다.** ponytail 의 사다리를 코드 쓰기 직전마다 밟는다:

```
1) 존재할 필요가 있나  2) 이 저장소에 이미 있나  3) 표준 라이브러리가 하나
4) 플랫폼 기본 기능인가  5) 설치된 의존성이 하나  6) 한 줄인가  7) 그다음에야 되는 최소한
```

⛔ **깎지 않는 것** — 신뢰 경계 검증 · 데이터 손실 처리 · 보안 · 접근성.
⚠️ `/ponytail-review` 는 **과설계만** 본다. **정확성 버그는 안 본다** — 테스트와 `/code-review` 가 그 몫이다.
⚠️ `/ponytail-review` 는 내장 `/simplify` 와 거의 겹친다. **둘 다 돌리지 않는다.**
⛔ **테스트 픽스처는 ponytail 지적에서 예외로 둔다.** 「투기적 추상화」 사냥에 픽스처가 걸릴 수 있는데,
판단 기준은 **「돌연변이를 넣었을 때 실패하는가」**이고 그것은 ponytail 이 보지 않는 축이다.
⚠️ 룰셋은 **세션 시작 시** 주입된다(매 턴이 아니다). 매 프롬프트에 도는 것은 모드 추적 훅이라 비용이 토큰이 아니라 **지연**이다.
⭐ **모드는 user 스코프**(`~/.claude/settings.json` 의 `env.PONYTAIL_DEFAULT_MODE`)다 — 프로젝트마다 설정하지 않는다.
